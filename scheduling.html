Simulating genomic data

The exercises in this chapter will pick up from where we left of in the chapter on building slendr demographic models, and use this as a basis to learn how to simulate genomic data from these models.

Preparation

To make sure we’re all on the same page, saving the following code in a new script slendr_scheduling.R. You can see that it’s basically the outcome of the exercises in the previous chapter on building demographic models with slendr.

library(slendr)
init_env()

p1 <- population("p1", time = 12000, N = 1000)
p2 <- population("p2", time = 9000, N = 1000, parent = p1)
p3 <- population("p3", time = 6000, N = 1000, parent = p2) %>%
  resize(N = 100, time = 1800) %>%
  resize(N = 2000, time = 1000)
p4 <- population("p4", time = 3000, N = 1000, parent = p3)

gf <- gene_flow(from = p2, to = p3, start = 3000, end = 2100, proportion = 0.1)

model <- compile_model(
    populations = list(p1, p2, p3, p4), gene_flow = gf,
    generation_time = 30,
    time_units = "years before present"
)

plot_model(model, proportions = TRUE)

Exercise: Simulating genomic data

Once we have compiled a slendr model, we can finally simulate data from it. By default, a simulation from a slendr model always produces a tree-sequence object as a result. We’ll explore the tree-sequence concept in a bit more detail later—for now we can treat it as a black box which “magically” stores genomic variation of a set of individuals.

There are two simulation engines built into slendr implemented by functions msprime() and slim(). For traditional, non-spatial, neutral demographic models, the msprime() engine is much more efficient, so we’ll be using that for the time being.

Note: The alternative engine implemented by the slim() function plays an important role for spatial simulations and for simulations of natural selection — these are the primary two reasons why it’s included in slendr in the first place.

As we discussed in the introduction, here’s how you can use simulate a tree sequence from a compiled slendr model. You will be seeing this kind of pattern over and over again, so it’s worth keeping it in mind any time you will be simulating data going forward.

ts <- msprime(
  model,
  sequence_length = <length of the simulated genome [in bp]>,
  recombination_rate = <uniform recombination rate [in crossovers per bp per generation]>
)

Simulate a tree sequence from your compiled model by adding the appropriate msprime() command into the script slendr_scheduling.R, storing it in a variable ts. Set the parameters sequence_length = 1e6 and recombination_rate = 1e-8.

NoteClick to see the solution

This command simulates a tskit tree sequence from a slendr model. Again, note that we don’t have to write any msprime or tskit code to implement the simulation because slendr does all the work for us!

ts <- msprime(model, sequence_length = 1e6, recombination_rate = 1e-8)

For instance, what are the “nodes” and “edges”? What’s the difference between “samples” and “individuals”? How many “trees” does the tree sequence have, and how many “mutations” are stored in it?

For instance, our tree sequence contains genomic information for 5000, each of them diploid. This makes for 10000 samples in total, where a “sample” is a “node” in a tree sequence representing one haplotype (i.e., one chromosome) of a simulated individual. All other “nodes” (of which there are many, many more) represent ancestral haplotypes of these recorded individuals for which we generally have only a part of their genomic information—a sequence information which made it through recombination to some of the recorded samples.

And notice that there are no mutations! How can this be possible, if we supposedly ran a genomic simulation? More on that later!

Note: Similarly to the symbol model, whenever we from now on refer to ts, we will be talking about some simulated tree-sequence object stored in an R variable ts.

Exercise: Referring to simulated individuals

If we are to use tree-sequence data for computation of population genomic statistics, we need a way to refer to individuals and populations. For this purpose, slendr provides three important functions: ts_recorded(), ts_names(), and (sometimes, but not often, also useful) ts_nodes(). At the bare minimum, these functions accept the tree sequence ts as their first argument (i.e., can be run such as ts_recorded(ts)).

  • How does ts_names() differ from the two table-producing functions?

Exercise: Customizing sample recording

We can see that our tree sequence contains a massive number of individuals. Too many, in fact — we recorded every single individual alive at the end of our simulation, which is something we’re unlikely to be ever lucky enough to have, regardless of which species we study.

To get closer to the scale of the genomic data that we usually work with, we can restrict our simulation to only record a subset of individuals—we do this using a process called “scheduling of recorded individuals” implemented by the slendr function schedule_recording(). Simply speaking, this is a functionality of slendr which precisely defines which individuals will be recorded in the tree sequence while ignoring everyone else.

The function follows the structure in the following snippet, representing another very useful pattern worth keeping in mind going forward:

schedule <- schedule_recording(
  <compiled slendr model>,
  times = <times of recording>,
  list(<population object>, <number of samples to record>),
  [... etc. ... ]
)

We then use this schedule object in a standard msprime() function call, setting it as the argument of the same name (schedule =) like this:

ts <- msprime(model, sequence_length = 1e6, recombination_rate = 1e-8, schedule = schedule)

To get an idea about what this function does in practice, modify the command which simulates the ts object in your script slendr_scheduling.R according to the snippet above, but include a schedule for recording 5 individuals from each of the four populations. When you re-run the new simulation to get a new ts object and type ts into your console, do you see a change? Again, use your knowledge of ts_recorded() and some dplyr table processing function to inspect the recorded individuals.

Hint: To make this easier to see, maybe keep the original simulation command in your script (the one without the schedule) but modify it to create a variable ts_big instead before you create the new ts object.

schedule <- schedule_recording(
  model,
  times = 0,
  list(p1, 5), list(p2, 5), list(p3, 5), list(p4, 5)

Exercise: Complex recording schedules

What if we need to simulate different number of individuals from different populations at very specific times? Doing this with a single call to schedule_recording() is not possible. Luckily, multiple schedules can be easily combined together into a single sampling schedule.

Type the schedule variable in your R console. What do you see? Why did I say that multiple schedules can be easily combined? And how could we combine them?

NoteClick to see the solution

The output of any schedule_recording() function is a plain old data frame! It contains a bunch of information we used in the schedule_recording() call (population names, times, etc.), plus a bunch more additional data which is currently irrelevant. For instance, notice the time, pop, and n columns below:

Normally we don’t ever have to look at this data (unless something goes wrong with the sampling and troubleshooting slendr itself is needed), but knowing the format of the schedule means we can easily combine multiple schedules using standard functions such as rbind() (included in base R).

In the following chapters, we will be working on implementing many real-world scenarios from widely established research in population genomics, particularly those from the field ancient DNA field. Naturally, in cases like this, we need to be able to simulate sequences of “ancient” individuals as well as various “present-day” reference panels.

In preparation for these complex exercises, implement the recording schedule summarized into the table below. 0 p1 1 outgroup
0 p2 1 admixture source
from 5 k B.P., every 1 k years p3 5 time-series of ancient individuals

Exercise: Recording of named individuals

Sometimes, we don’t just want to record a given set of “anonymous” individuals, but we want to be able to work with unique, named individuals. This can be especially helpful when we want to reconstruct a particular scenario in some specific archaeological context (for instance, we want to work with some very precious archaeological sample, such as the “Altai Neanderthal”).

We can do so by calling schedule_recording() in a slightly modified way which doesn’t use the normal syntax list(<population>, <number>), to record a given number of individuals from the given population, but instead uses the format of list(<population>, 1, "<name of the individual>").

Use this format to modify your recording schedule (for instance, based on combining two recording schedules called modern and ancient) to implement a unique recording event which will give the one representative individual of the admixture source population the name "source_ind" and the outgroup individual will be named "outgroup_ind". Then create a new combined schedule again, and verify that you got the newly named individuals in a new simulated tree sequence ts.

NoteClick to see the solution

We’ll be more succinct now (see the full explanation to the modern and ancient schedules in the solution to the previous exercise):

outgroup <- schedule_recording(model, times = 0, list(p1, 1, "outgroup_ind"))
source<- schedule_recording(model, times = 0, list(p2, 1, "source_ind"))
modern <- schedule_recording(model, times = 0, list(p1, 1), list(p4, 10))
ancient <- schedule_recording(model, times = seq(5000, 1000, by = -1000), list(p3, 5))

schedule <- rbind(outgroup, source, modern, ancient)

Now we can simulate a new tree sequence with more specifically named individuals:

ts <- msprime(model, sequence_length = 1e6, recombination_rate = 1e-8, schedule = schedule)

And verify that we did everything correctly by inspecting the table of the contents of the tree sequence:

You may have noticed that plot_model() has a number of optional arguments. One of them is called schedule and it accepts a sampling schedule (such as the one you just created) as its input. Use your model and sampling schedule to visualize your model.

This functionality can be useful as an additional validation of your modeling scripts, so always remember to use this for sanity checking your simulations (after all, a picture can be worth more than thousand words dozens of lines of code)!

NoteClick to see the solution

Here’s is the model on its own:

plot_model(model)

Here is the model with sampling numbers overlaid on top:

plot_model(model, schedule = schedule)

Note: As you’ve seen above, the visualization is often a bit wonky and convoluted with overlapping elements, so don’t be too frustrated if the results of your plot_model() visualizations are not too pretty. The function has been designed as a validation and troubleshooting tool, rather than a tool to create publication-ready figures.

library(slendr)
init_env()

p1 <- population("p1", time = 12000, N = 10000)
p2 <- population("p2", time = 9000, N = 2000, parent = p1)
p3 <- population("p3", time = 6000, N = 5000, parent = p2)
p4 <- population("p4", time = 3000, N = 2000, parent = p3)

gf <- gene_flow(from = p2, to = p3, start = 3000, end = 2100, proportion = 0.1)

model <- compile_model(
    populations = list(p1, p2, p3, p4), gene_flow = gf,
    generation_time = 30,
    time_units = "years before present"
)

outgroup <- schedule_recording(model, times = 0, list(p1, 1, "outgroup_ind"))
source<- schedule_recording(model, times = 0, list(p2, 1, "source_ind"))
modern <- schedule_recording(model, times = 0, list(p1, 1), list(p4, 10))
ancient <- schedule_recording(model, times = seq(5000, 1000, by = -1000), list(p3, 5))

schedule <- rbind(outgroup, source, modern, ancient)

plot_model(model, proportions = TRUE, schedule = schedule)

ts <- msprime(model, sequence_length = 1e6, recombination_rate = 1e-8, schedule = schedule)
