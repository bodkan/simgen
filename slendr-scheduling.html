Catch up

The exercises in this chapter will pick up from where we left of in the chapter on building slendr demographic models. To catch up, feel free to use the following script as a basis for what’s coming up next:

library(slendr)
init_env()

p1 <- population("p1", time = 12000, N = 1000)
p2 <- population("p2", time = 9000, N = 1000, parent = p1)
p3 <- population("p3", time = 6000, N = 1000, parent = p2) %>%
  resize(N = 100, time = 1800) %>%
  resize(N = 2000, time = 1000)
p4 <- population("p4", time = 3000, N = 1000, parent = p3)

gf <- gene_flow(from = p2, to = p3, start = 3000, end = 2200, proportion = 0.1)

model <- compile_model(
    populations = list(p1, p2, p3, p4), gene_flow = gf,
    generation_time = 30,
    time_units = "years before present"
)

plot_model(model, proportions = TRUE)

Exercise: Simulating genomic data

Once we have compiled a slendr model and stored it in a variable, we can finally simulate data from it. By default, a simulation from a slendr model always produces a tree-sequence object as a result. We’ll explore the tree-sequence concept in a bit more detail later, but for now we can treat it as a black box which somehow “magically” stores genomic variation of a set of individuals.

Note: As discussed in our introduction to this session, tree sequences provide an extremely efficient means to store and work with genomic data at a massive scale. However, you can always get simulated data even in traditional file formats, such as VCF, EIGENSTRAT, or a plain table of ancestral/derived genotype states.

In this section, we will be only working with tree sequences, because it’s much easier and faster to get interesting statistics from it directly in R, but you can always compute the same statistics from simulated VCF or EIGENSTRAT files using any of the available software methods as well.

There are two simulation engines built into slendr implemented by functions msprime() and slim(). For traditional, non-spatial, neutral demographic models, the msprime() engine is much more efficient, so we’ll be using that for the time being. However, it’s worth noting that from the perspective of population genetics theory, both simulation functions will give you practicalyl the same results for any given compiled slendr model (up to some level of stochastic noise).

Note: The alternative engine implemented by the slim() function plays an important role for spatial simulations and for simulations of natural selection — these are the primary two reasons why it’s included in slendr in the first place.

As we discussed in the introduction, here’s how you can use simulate a tree sequence from a compiled slendr model. You will be seeing this kind of pattern over and over again, so it’s worth keeping it in mind any time you will be simulating data going forward.

ts <- msprime(
  model,
  sequence_length = <length of the simulated [bp]>,
  recombination_rate = <uniform recombination rate [crossovers per bp per generation]>
)

Simulate a tree sequence from your compiled model using the msprime() engine and store it in a variable ts as shown in the snippet of code right above. Set the parameters sequence_length = 1e6 (length of the sequence in bp) and recombination_rate = 1e-8 (crossover events per base pair per generation).

This command simulates a tskit tree sequence from a slendr model. Again, note that we don’t have to write any msprime or tskit code to implement the simulation because slendr does all the work for us!

For instance, our tree sequence contains genomic information for {r} ts$num_individuals, each of them diploid. This makes for {r}ts$num_samples samples in total, where a “sample” is a “node” in a tree sequence representing one haplotype (i.e., one chromosome) of a simulated individual. All other “nodes” (of which there are many, many more) represent ancestral haplotypes of these recorded individuals for which we generally have only a part of their genomic information—a sequence information which made it through recombination to some of the recorded samples.

Note: Similarly to the symbol model, whenever we from now on refer to ts, we will be talking about some simulated tree-sequence object stored in an R variable ts.

In the ts summary, you probably noticed there are no mutations! As we will see later, the magic of tree sequences allows us to compute nearly any conceivable population genetic statistic even without mutations. That said, particularly for exploring statistics computed by various third-party software outside of R, having mutations can be often useful.

Modify the part of your script which simulates the ts object, adding a %>% ts_mutate(mutation_rate = 1e-8) after the msprime(...) function call. After you execute this new command and type ts in the R console to inspect the summary, you should see that mutations have been added.

Note: Even though mutations are generally not needed, there’s almost never any huge downside to adding them, so I recommend you always use both msprime() and ts_mutate() in your models.

Here’s the general pattern of how we simulate genomic data with slendr including mutations:

ts <-
  msprime(model, sequence_length = 1e6, recombination_rate = 1e-8) %>%
  ts_mutate(mutation_rate = 1e-8)

We can see that, indeed, the tree sequence now has 998 mutations in it.

Exercise: Scheduling sampling events

We can see that our tree sequence contains a massive number of individuals. Too many, in fact — we recorded every single individual alive at the end of our simulation, which is something we’re unlikely to be ever lucky enough to have, regardless of which species we study.

To get closer to the scale of the genomic data that we usually work with, we can restrict our simulation to only record a subset of individuals—we do this using a process called “scheduling of recorded individuals” implemented by the slendr function schedule_sampling(). Simply speaking, this is a functionality of slendr which precisely defines which individuals will be recorded in the tree sequence while ignoring everyone else.

The function follows the structure in the following snippet, representing another very useful pattern worth keeping in mind going forward:

schedule <- schedule_sampling(
  <compiled slendr model>,
  times = <numbers representing times of recording>,
  list(<population>, <number of samples to record>),
  list(<population>, <number of samples to record>)
  [... etc. ]
)

We then use this schedule object in a standard msprime() function call, setting it as the argument of the same name, i.e. like this:

ts <-
  msprime(model, sequence_length = 1e6, recombination_rate = 1e-8, schedule = schedule) %>%
  ts_mutate(mutation_rate = 1e-8)

To get an idea about what this function does in practice, modify the command which simulates the ts object in your script according to the snippet above, but include a schedule for recording 5 individuals from each of the four populations. When you run a new simulation and type the ts object name into your console, do you see a change? Use your knowledge of ts_samples() and some tidyverse table processing to inspect the recorded individuals.

Hint: To make this easier to see, maybe keep the original simulation command in your script (the one without the schedule) but modify it to create a variable ts_big instead.

Exercise: Composing complex recording schedules

What if we need to simulate different number of individuals from different populations at very specific times? Doing this with a single call to schedule_sampling() is not possible. Luckily, multiple schedules can be easily combined together into a single sampling schedule.

Type the schedule variable in your R console. What do you see? Why did I say that multiple schedules can be easily combined? And how could we combine them?

NoteClick to see the solution

The output of any schedule_sampling() function is a plain old data frame! It contains a bunch of information we used in the schedule_sampling() call (population names, times, etc.), plus a bunch more additional data which is currently irrelevant.

Normally we don’t ever have to look at this data (unless something goes wrong with the sampling, like when a bug in slendr is encountered), but knowing the format of the schedule means we can easily combine multiple schedules using standard functions such as rbind() (included in base R) or bind_rows() (included in the tidyverse package dplyr).

In the following chapters, we will be working on implementing many real-world scenarios from widely established research in population genomics, particularly those from the field ancient DNA field. Naturally, in cases like this, we need to be able to simulate sequences of “ancient” individuals as well as various “present-day” reference panels.

It looks like we have effectively two groups of sampling events determined by the times indicated in the first column: sampling of individuals in the “present-day” (i.e., at time 0) and sampling of individuals in the past. So let’s leverage that to create two sampling schedules, “modern” and “ancient”:

Scheduling of modern individuals:

modern <- schedule_sampling(model, times = 0, list(p1, 1), list(p2, 1), list(p4, 10))

Scheduling of ancient individuals:

ancient_times <- seq(5000, 1000, by = -1000)

ancient <- schedule_sampling(model, times = ancient_times, list(p3, 5))

We can then create a single sampling schedulie like this:

schedule <- rbind(modern, ancient)

And use it in our simulation just like we showed above:

ts <-

  ts_mutate(mutation_rate = 1e-8)

Exercise: Scheduling the sampling of named individuals

Sometimes, we don’t just want to record a given set of “anonymous” individuals, but we want to be able to work with unique, named individuals. This can be especially helpful when we want to reconstruct a particular scenario in some specific archeological context (for instance, we want to work with some very precious archaeological sample, such as the “Altai Neanderthal”).

We can do so by calling schedule_sampling() in a slightly modified way which doesn’t use the normal syntax list(<population>, <number>), to record a given number of individuals from the given population, but instead uses the format of list(<population>, 1, "<name of the individual>").

Use this format to modify your sampling schedule (for instance, based on combining two sampling schedules called modern and ancient) to implement a unique sampling event which will give the one representative individual of the admixture source population the name "source_ind" and the outgroup individual will be named "outgroup_ind". Then create a new combined sampling schedule again, and verify that you got the new samples in a new simulated tree sequence ts.

NoteClick to see the solution

We’ll be more succint now (see the full explanation to the modern and ancient schedules in the solution to the previous exercise):

outgroup <- schedule_sampling(model, times = 0, list(p1, 1, "outgroup_ind"))
source<- schedule_sampling(model, times = 0, list(p2, 1, "source_ind"))
modern <- schedule_sampling(model, times = 0, list(p1, 1), list(p4, 10))
ancient <- schedule_sampling(model, times = seq(5000, 1000, by = -1000), list(p3, 5))

schedule <- bind_rows(outgroup, source, modern, ancient)

Now we can simulate a new tree sequence with more specifically named individuals:

ts <-
  msprime(model, sequence_length = 1e6, recombination_rate = 1e-8, schedule = schedule) %>%
  ts_mutate(mutation_rate = 1e-8)

You may have noticed that plot_model() has a number of optional arguments. One of them is called schedule and it accepts a sampling schedule (such as the one you just created) as its input. Use your model and sampling schedule to visualize your model.

This functionality can be useful as an additional validation of your modeling scripts, so always remember to use this for sanity checking your simulations (after all, a picture can be worth more than thousand words dozens of lines of code)!

NoteClick to see the solution

Here’s is the model on its own:

plot_model(model)

Here is the model with sampling numbers overlaid on top:

plot_model(model, schedule = schedule)

Note: As you’ve seen above, the visualization is often a bit wonky and convoluted with overlapping elements, so don’t be too frustrated if the results of your plot_model() visualizations are not too pretty. The function has been designed as a validation and troubleshooting tool, rather than a tool to create publication-ready figures.
