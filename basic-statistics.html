Within-population statistics

Theme of this chapter

Now that we have a slendr model encoded in a reproducible R script and a simulated genomic data in the form of a tree sequence ts, how can we compute population genetic statistics from this data?

Computing statistics requires a specification of what should be computed and how. For instance, which individuals should a computation be performed on? If groups of multiple individuals are involved then how do we group them?

Exercises in this chapter will demonstrate these techniques using the most fundamental concepts of population genomics, namely \(N_e\), nucleotide diversity, and allele frequency spectrum. Rather than delving into the mathematical underpinning of these statistics, they will be used to provide a familiar context to show how easy it is to gain insight into (sometimes unintuitive) behavior of statistics in general through simulation-based exploration.

More concretely, the coding exercises will focus on the testing of a hypothetical inference method (using a toy example of \(N_e\) inference) using simulation-based benchmarking across a parameter grid.

Literature

In case you find yourself with extra time for some background reading, I recommend the following two chapters from the absolutely brilliant, freely-available textbook called “An Owner’s Guide to the Human Genome”. I don’t think there’s better companion resource on population genomics theory to what I’m trying to do in this practical, simulation-based workbook.

  • Chapter 2.1, “Genetic Drift: What happens to alleles over time?”: A beautiful and simple introduction to the concept of effective population size, the effect of genetic drift and mutation on the amount genetic diversity in a population, Wright-Fisher model, etc. (i.e, the core ideas we explore in this chapter through population genomic simulations).

  • Chapter 2.2, “More on genetic drift: The coalescent.”: A slightly more technical (yet still very easy to digest) dive into the coalescent theory background of the topics introduced in the previous chapter (and, therefore, also to the simulation exercises in this chapter), including discussion of the allele frequency spectrum (AFS).

Exercise 2: Within-group(s) statistics — nucleotide diversity

The simplest possible computation we can do is to compute a statistic for a single population. As an example, let’s look at nucleotide diversity (also known as \(\pi\)), implemented by the slendr function ts_diversity().

If you look at its help page under ?ts_diversity, you will see that it accepts several arguments—for now let’s focus on the first two, ts = (which is obviously a tree-sequence object, such as the one produced by the msprime() engine) and sample_sets =.

Compute ts_diversity() on a single simulated individual, such as the individual with the name “pop_1”, by providing this name as the sample_sets = argument of this function. Knowing that slendr simulates diploids and knowing the definition of nucleotide diversity, how would you interpret the result that you get for this one individual from the perspective of genomics?

NoteClick to see the solution

The answer is that we get that individual’s heterozygosity—the proportion of their complete genome (composed of two chromosomes, because each individual is diploid) carrying heterozygous sites:

ts_diversity(ts, sample_sets = "pop_1")
# A tibble: 1 × 2
  set   diversity
  <chr>     <dbl>
1 pop_1  0.000216

Note that this is the same thing as the following command:

ts_diversity(ts, sample_sets = c("pop_1"))
# A tibble: 1 × 2
  set   diversity
  <chr>     <dbl>
1 pop_1  0.000216

This is because in R, a single value is the same thing as a vector of length one (this might seem like a bit of curious R trivia but it’s good to keep in mind):

"single_value" == c("single_value")
[1] TRUE
length(c("single_value"))
[1] 1
length("single_value")
[1] 1

Now run the following three commands, one after the other. They look extremely similar, right? Do they produce the same value? If not, based on the results you get from each of those commands, can you deduce a general rule for how slendr interprets what it gets in the sample_sets = argument?

ts_diversity(ts, sample_sets = c("pop_1", "pop_42"))
ts_diversity(ts, sample_sets = list(c("pop_1", "pop_42")))
ts_diversity(ts, sample_sets = list(pop_subset = c("pop_1", "pop_42")))

Note: It turns out that patterns like these are very important for computing any kind of tree-sequence statistic with slendr, so it very much pays off to think about this, even though this looks trivial and nitpicky!

NoteClick to see the solution
  • The first command is supposed to demonstrate that specifying a plain vector of names to a statistic computed within a group computes that statistic as if each individual was “its own group”. In this example, we get individual-based heterozygosity for each of the two individuals separately (notice that the “pop_1” value is the same you got in the previous task):
ts_diversity(ts, sample_sets = c("pop_1", "pop_42"))
# A tibble: 2 × 2
  set    diversity
  <chr>      <dbl>
1 pop_1   0.000216
2 pop_42  0.000192
  • The second command features the same vector of names, but wrapped in list(). This is how you instruct slendr to treat a given set of individuals as a group—and in this case, compute a statistic for the group as a whole. In this context, this command computes the nucleotide diversity within a group formed by the given two individuals from the population “pop”:
ts_diversity(ts, sample_sets = list(c("pop_1", "pop_42")))
# A tibble: 1 × 2
  set   diversity
  <chr>     <dbl>
1 set_1  0.000204
  • Notice that in the result above, slendr assigned our group of two individuals a rather non-descriptive group name “set_1”. Because these default names can be confusing in more complex computations of more complex statistics, you can optionally specify the name of your group by providing the set of individuals as a named list instead (see the R bootcamp chapter in case you need a refresher on named lists and similar topics):
# note that the group name "set_1" is now replaced by "pop_subset"
ts_diversity(ts, sample_sets = list(pop_subset = c("pop_1", "pop_42")))
# A tibble: 1 × 2
  set        diversity
  <chr>          <dbl>
1 pop_subset  0.000204

Of course, we can compute any statistic not only for one group of individuals, but for multiple of them. What result such computation produces depends on whether we’re computing the so-called “one-way statistics” (computed within groups, like nucleotide diversity we started with here) or “multi-way statistics” (computed between groups, like \(F_{ST}\)). For now we’ll stay with one-way statistics.

To make the “one-way” statistic concept clear, let’s practice this. Instead of computing ts_diversity() for a single group of individuals (like “pop_1” and “pop_42” above), compute it on multiple subsets of individuals of increasing samples sizes (let’s say groups of 1, 2, 5, 10, 500 1000, and finally all individuals in the population “pop”). Before you run this computation, do you expect the same value of nucleotide diversity for each of those sample sizes? Why, or why not?

Hint: You can get a random subset of a larger set of elements using the built-in R function sample(). Take a look at ?sample manual page if you need more help. If you need even more help, take a peek at the beginning of the solution below (point 2. specifically). When you have a list of the different subsets of individuals, you can provide it as the sample_sets = argument of ts_diversity() again.

NoteClick to see the solution

Let’s first generate the subsets of different sizes. We have a number of options:

  1. We could do it “manually” like this:
# first get all names of all individuals recorded in the tree sequence
# as a single vector stored in the variable named `all`
all <- ts_names(ts)

# then "manually" create all required subsets
subsets <- list(
  sample(all, 1),
  sample(all, 2),
  sample(all, 5),
  sample(all, 10),
  sample(all, 500),
  sample(all, 1000),
  all
)
  1. Alternatively, we could do it more succinctly using this neat R trick:
# first create a vector of the desired sizes of all subsets
sizes <- c(1, 2, 5, 10, 500, 1000, length(all))

# then iterate over those sizes, applying the sample() function to each
subsets <- lapply(sizes, sample, x = all)
names(subsets) <- sizes

Either way, both approaches create a list of vectors of appropriate lengths that we need to solve this exercise.

Having created the lists of subsets of individuals from the population, we can finally compute nucleotide diversity in each of those groups like this:

ts_diversity(ts, sample_sets = subsets)
# A tibble: 7 × 2
  set   diversity
  <chr>     <dbl>
1 1      0.000210
2 2      0.000207
3 5      0.000209
4 10     0.000201
5 500    0.000206
6 1000   0.000206
7 5000   0.000206

Not surprisingly, we don’t see much difference. This is expected, because there is only one true (unknown) value of nucleotide diversity of the entire population. What changes when we compute this statistic on subsets of different sizes is the stochastic noise due to random chance.

We’ll see a bit more on how to control (and quantify) the noise in simulations a little bit later.

Exercise 3: Parameter estimation — \(N_e\)

In practical research, we often use various software to estimate some model parameter of interest. In our context—again, to demonstrate the concept of simulation-based analyses in a familiar context—let’s look at a measure of the population size called effective population size, or \(N_e\), as this model parameter of interest we want to infer.

From a bit of background theory of population genetics, we know that we can obtain an estimate of \(N_e\) from nucleotide diversity (which we just computed). Specifically, neutral theory of molecular evolution posits that an idealised diploid population will have the nucleotide diversity (usually called \(\theta\) in literature) equal to

\[\theta = 4 N_e \mu,\]

where \(\mu\) is the mutation rate. Using simple algebra to rearrange this equation, this gives us an estimate for \(N_e\) which can be computed from nucleotide diversity in the form of

\[N_e = \frac{\theta}{4 \mu}.\]

In principle, this is an estimate which could be computed by some external software (in a more complex real-world scenario). Let’s build a simple simulation-based analysis to determine how well does this estimator perform under different scenarios.

Note: If you are familiar with population genetics, this exercise has all sorts of obvious answers, but let’s demonstrate how we can benchmark this estimate using simulations, establishing a useful slendr recipe which you will be able to use in many other contexts on many other inference methods (some of the more complex ones will be demonstrated later in this workshop).

In your script slendr_statistics.R, start by computing nucleotide diversity across all individuals in your tree sequence taken together (instead of a small subset) and store this result of ts_diversity() in a data frame df. Then, use the equation above to estimate \(N_e\) from nucleotide diversity, adding a new column called Ne_estimated to this data frame with this value. Do you get a somewhat reasonably looking result?

Hint: Remember that you know the true \(N_e\) in your model — it’s the N value in your simulation script! That’s the most powerful thing about simulations — they allow you to establish a ground truth and benchmark various methods against this truth!

NoteClick to see the solution

Let’s get the data frame with the value of diversity first:

df <- ts_diversity(ts, list(all = ts_names(ts)))
df
# A tibble: 1 × 2
  set   diversity
  <chr>     <dbl>
1 all    0.000206

Then add the inferred \(N_e\) according to the equation above:

df$Ne_estimated <- df$diversity / (4 * 1e-8)
df
# A tibble: 1 × 3
  set   diversity Ne_estimated
  <chr>     <dbl>        <dbl>
1 all    0.000206        5148.

We programmed the true \(N_e\) in our model at 5000, so this estimate doesn’t look bad at all!

Of course, benchmarking any method based on a single simulation of a single number doesn’t make much sense in practice—so now let’s now take things one step forward.

Exercise 4: Generalizing the simulation

Suppose we need to evaluate how our hypothetical statistic of interest (in this example, our estimator of \(N_e\)) behaves under different parameters, different models, different bioinformatic processing, etc. This happens very often in practical research, so how would we go about it using simulations?

To do this, we could make a copy of our original script, modify it a bunch of times, and re-run the modifications as needed, collecting the results in the process. This works, but is almost always the wrong approach. The correct way to do this is to generalize our code into a self-contained function.

To demonstrate, let’s break this down into individual steps (in software engineering, this process of modifying code and improving it is called “refactoring”).

First, save your current script slendr_statistics.R as a new script called slendr_Ne_pi.R. We’ll be working on improvements in this new file (the pi comes from a shortcut name for nucleotide diversity in mathematical theory \(\pi\)).

In this new script slendr_Ne_pi.R, create a new R function called sim_constant, which will accept a single argument Ne_true, and will “wrap around” the following bits of code (most of which can be copy-pasted from the original slendr_statistics.R you worked on so far in this chapter, with minor modifications):

  1. the code implementing our slendr demographic model (substituting the originally fixed N value for Ne_true, of course),

  2. the command simulating a ts object from the model,

  3. the command creating the df data frame with nucleotide diversity,

  4. the computation of Ne_estimated from nucleotide diversity,

  5. addition of a Ne_true column to df and assigning it the Ne_true argument given to your function.

  6. returning this df object as the output of the function.

When you’re done, all code which was doing the steps above in your original script should be entirely replaced by this function.

Hint: If you need help with creating a custom function, you can use the following template which shows what should your script look like when you’re done. Additionally, you can get a refresher on programming custom functions by skimming the relevant section of the “R bootcamp” chapter.

library(slendr)

  # add the bits of code doing steps 1.-5. inside this function

  # finally, return the df data frame like this (step 6.)

NoteClick to see the solution

Here’s how my entire slendr_Ne_pi.R looks like. As you can see, it’s basically the same exact code as the script slendr_statistics.R we started with, just “wrapped” in the function(Ne_true) { ... } block.

library(slendr)
init_env()

sim_constant <- function(Ne_true) {
  pop <- population("pop", time = 2001, N = Ne_true)
  
  model <- compile_model(populations = pop, generation_time = 1, direction = "backward")

  ts <-
    msprime(model, sequence_length = 10e6, recombination_rate = 1e-8) %>%
    ts_mutate(mutation_rate = 1e-8)

  df <- ts_diversity(ts, list(all = ts_names(ts)))

  df$Ne_estimated <- df$diversity / (4 * 1e-8)

  df$Ne_true <- Ne_true
  
  df
}

Then, evaluate your function in the R console by running it for different values of \(N_e\) (for instance, type sim_constant(100), sim_constant(1234), sim_constant(20000), etc.). Each of your function calls should produce a data frame with the appropriate value of diversity and the estimated \(N_e\).

Doing all this extra programming work might seem like unnecessary bother. In fact, it looks like we’ve written even more code to make this happen! But the pay off comes later, I promise.

Custom functions are absolutely critical for efficient, reproducible science. They eliminate copy-pasted bug-prone code and make it much easier to explore ideas, test parameters, and explore various models. In this workshop, I’ll be often forcing you to write custom functions—hopefully, by the end you will appreciate why I did this.

Exercise 5: Simulations across parameter grids

Whenever we want to benchmark a statistic or understand its expected behavior under different circumstances, we need to re-run a model many times, usually for different model parameters (or even different models entirely).

Imagine we want to repeat our inference on many different potential values of true \(N_e\). What we could do is something like what you did while testing your function earlier, running the variations of the simulation individually and manually. But this isn’t scalable, definitely not if we need to run the same model across a huge number of parameter values (or even multiple sets of such parameters).

In cases like this, we can use a “looping” function, such as the very convenient function map_dfr() from the package purrr.

Let’s demonstrate how this technique works. You don’t have to run any of this code, just skim through this demonstration to get an idea how this works and apply it later.

Imagine a silly little function like this, which creates a data frame with a given number and its square:

# define a custom function
silly_fun <- function(x) {
  return(data.frame(value = x, squared = x * x))
}

# run it for the value of x = 10
silly_fun(10)
  value squared
1    10     100

The way you use map_dfr is by providing a list of values of our parameter of interest and a name of some function. In the case of our silly function, we can use map_dfr() like this:

library(purrr)

map_dfr(c(10, 100, 1234, 20000), silly_fun)
  value   squared
1    10       100
2   100     10000
3  1234   1522756
4 20000 400000000

The name map_dfr stands for “map a given function producing a data frame and then bind its rows together”, hence, map_dfr. When you look at its output above, this is exactly what happened.

In your script slendr_Ne_pi.R, use the same technique program an automated simulation of \(N_e\) inference across a grid of Ne_true values of c(1000, 2000, 3000, 4000, 5000, 10000, 15000, 20000). Use the function map_dfr() to do this in an efficient, automated way, thus obtaining a single data frame. Then, visualize the results in this data frame as a scatterplot of columns Ne_true against Ne_estimated. You can use ggplot2, or base-R plotting, whatever you find easier.

NoteClick to see the solution 
library(ggplot2)
library(purrr)

Ne_grid <- c(1000, 1500, 2000, 2500, 3000, 4000, 5000, 10000, 15000, 20000)

df_constant <- map_dfr(Ne_grid, sim_constant)

ggplot(df_constant, aes(Ne_true, Ne_estimated)) +
  geom_point() +
  geom_abline(slope = 1, color = "red", linetype = "dashed") +
  ggtitle("True Ne vs Ne estimated from nucleotide diversity (constant population size)")

This toy exercise is a great example of how to use these kinds of simulations in practice. Again, nucleotide diverisity-based \(N_e\) estimation and its benchmarking across a range of parameters is only an example for demonstration, but this idea extends to many other settings:

  • benchmarking of IBD accuracy across different gene-flow scenarios,

  • validating qpAdm inference results for various possible admixture graphs,

  • testing the robustness of local ancestry inference methods (LAI) and admixture dating inference as a function of admixture times and proportions,

  • understanding how PCA differs for different sample sizes from different populations,

… and many others.

Exercise 6: Comparing multiple models

Let’s make it a bit more interesting and more practically relevant. Suppose we want to see how robust our estimator is to the assumptions behind the underlying demographic model (which is almost always uncertain to some degree, meaning that our assumptions can be also uncertain!).

In the previous exercise, we used nucleotide diversity to infer the \(N_e\) of a population under study (we used an equation, but it could be also external software) and verified that it works very well for a model of a constant population size.

But what about population that experienced a resize event? How well does our \(N_e\) estimate work in such case?

In your script slendr_Ne_pi.R, make a copy of your function sim_constant() and name that copy sim_change(). Make the following changes to this function:

  1. the population “pop” will start with fixed \(N_e\) of 5000,

  2. the population will experience a population resize (implemented by the function resize()), which will set the size of the population to the value given to the argument Ne_true at time 1000.

Then, use map_dfr() to run the new function sim_change() along the same parameter grid as before, visualizing the results of Ne_true against Ne_estimated again. How well does our diversity-based \(N_e\) estimate perform in such a demographic scenario? Is it robust to non-constant demographic histories? If not, why?

NoteClick to see the solution

Here’s the solution—new function sim_change(), new simulation run against a parameter grid, and a visualization of results:

# new function to simulate population size change
sim_change <- function(Ne_true) {
  pop <-
    population("pop", time = 2001, N = 5000) %>%
    resize(N = Ne_true, time = 1000)
  
  model <- compile_model(populations = pop, generation_time = 1, direction = "backward")

  ts <-
    msprime(model, sequence_length = 10e6, recombination_rate = 1e-8) %>%
    ts_mutate(mutation_rate = 1e-8)

  df <- ts_diversity(ts, list(all = ts_names(ts)))

  df$Ne_estimated <- df$diversity / (4 * 1e-8)

  df$Ne_true <- Ne_true
  
  df
}

We can see that even a large population resize event doesn’t change the observed levels of nucleotide diversity that much. As a result, the \(N_e\) based on the population nucleotide diversity is very wrong—we consistently estimate it at the level of 5000 (i.e., the size prior to the resize), regardless of the true size of the population after the resize.

It’s only very drastic bottlenecks that are picked up by our \(N_e\) estimator, and even in those cases we still severely overestimate the true \(N_e\) after the resize event.

Exercise 7: Expanding the parameter grid

Our hypothesis for how poorly the nucleotide diversity-based estimate of \(N_e\) is doing under non-constant population size is that the resize event is very recent. As a result, diversity hasn’t yet reached an equilibrium value which would be picked up by our \(N_e\) estimator.

Let’s test this hypothesis while, at the same time, showing how we can expand the parameter grid simulations to include another parameter—this time the time of the population size change in addition to the \(N_e\) resize value.

In your script slendr_Ne_pi.R, add a second argument to your function sim_change() called T_change. Change the resize() command in your function to use variable T_change instead of the fixed value of 1000, then add another column called T_change to the data frame with the value of this argument before the function returns the results again. Then, run four versions of the map_dfr() command in the same way as before, except now in the form such as map_dfr(Ne_grid, sim_change, T_change = 100) (this will run sim_change() for each of the Ne_grid values like before, while fixing the T_change parameter to 100). Do this for T_change of 1, 100, 1000, and 2000.

When you visualize the results for each of the four simulation batches, do you see evidence supporting our hypothesis for why our \(N_e\) estimator performs poorly in sudden changes of \(N_e\)? And does the time since the resize change have an effect on the estimator as we hypothesized?

  df$T_change <- T_change

}

We can see that, indeed, the older the population resize event, the more time there’s for the population to lose genetic variation (in case of a bottleneck), or gain new variation (in case of population size increase—though we don’t really see the effect here), which means that the \(N_e\) estimated based on the \(\theta = 4 N_e \mu\) nucleotide diversity parameter is going to be a little closer to the true (unknown) population size.

Still, it’s absolutely clear that non-constant demography can completely mislead the \(N_e\) estimator based on nucleotide diversity—this is a conclusion that is actually quite relevant for real-world applications. For instance, we could have very endangered species (with a very small \(N_e\)) which still maintains quite a bit of nucleotide diversity!

In conclusion, the problem with the nucleotide diversity is that it effectively reduces the entirety of genetic variation in the population (which mutations there are at which frequencies) into a single number. As a result, we lose a lot of potentially very useful information about the population’s demographic history. When we try to estimate \(N_e\) using this summary statistic, we can only hope to infer a long-term \(N_e\), but we won’t be able to infer recent population dynamics.

As we have seen, a single bottleneck doesn’t cause nucleotide diversity to drop significantly enough for us to pick up that this bottleneck even happened.

But does the AFS really carry more information about demographic changes?

Write a new function in your script, called sim_afs(), which will again accept a single argument Ne_true and implement the exact same demographic model as you did in your function sim_change() (i.e., resize from the initial N of 5000 to the given value of Ne_true at time 1000). In this function, compute the afs vector from this model, then run it for a range of Ne_grid values and visualize the individual AFS vectors produced for each of them. Does AFS pick up signal even from such recent population size changes, unlike the nucleotide diversity?

NoteClick to see the solution

Here’s a function which simulates an AFS for a demographic history given by the Ne_true argument:

library(ggplot2)
library(purrr)
library(dplyr)

library(slendr)
init_env()

sim_afs <- function(Ne_true) {
  pop <- population("pop", time = 2001, N = 5000) %>% resize(N = Ne_true, time = 1000)

  model <- compile_model(populations = pop, generation_time = 1, direction = "backward")

  ts <-
    msprime(model, sequence_length = 10e6, recombination_rate = 1e-8) %>%
    ts_mutate(mutation_rate = 1e-8)

  subset <- sample(ts_names(ts), 10)
  
  afs <- ts_afs(ts, sample_sets = list(subset))
  
  # return the result not as a plain integer vector, but a proper data frame
  # annotated by the frequency bin number -- this makes visualization of
  # results later with ggplot2 much easier
  data.frame(
    Ne_true = Ne_true,
    frequency = 1:length(afs),
    count = afs
  )
}

We run the AFS simulation batch in the same way as we did before:

df_afs <- map_dfr(Ne_grid, sim_afs)

And we visualize the individual AFS vectors, colored by their underlying assumed \(N_e\) after the demographic history change:

ggplot(df_afs, aes(frequency, count, color = factor(Ne_true))) +
  geom_line() +
  ggtitle("AFS vector for different population size change models")

For easier comparison, here are the AFS result side-by-side with the values of nucleotide diversity from the same demographic scenarios:

`geom_smooth()` using method = 'loess' and formula = 'y ~ x'

This simulation indicates that AFS does, indeed, carry much more information about population history, even for recent changes in population size, driven largely by singletons! Therefore, at least for population expansions, AFS is much more statistically powerful than nucleotide diversity. From population genetic theory perspective this makes sense, because nucleotide diversity is actually nothing but a summary of the AFS.
