Computing within-population statistics

Computing population genetic statistics requires a specification of what should be computed and how. Which individuals should a computation be performed on? If multiple individuals should be grouped together, how do we define these groups?

This chapter will teach you how to do this with slendr by guiding you through exercises focused on the most fundamental concepts of population genomics. The focus will be less on teaching you how these concepts work (after all, you might be already be quite familiar with population genetics from your studies or work) and more to give you the opportunity to learn the technicalities of R and slendr in a familiar context.

That said, I have designed the exercises to provide interesting puzzles to showcase the usefulness of simulation-based exploration even in (seemingly) basic scenarios and applications, so that even readers relatively well familiar with population genomics will appreciate a new perspective on familiar topics. Every single one of them represents a question I myself had, and my solutions are the means I used myself to get the answers.

Preparation

Let’s start with the following single-population model to keep things as simple as possible. Look through the code to understand what it does, then save it as slendr_statistics.R. Run the entire script and inspect the produced visualization to make sure your understanding is correct.

library(slendr)
init_env()

pop <- population("pop", time = 2001, N = 5000)

model <- compile_model(populations = pop, generation_time = 1, direction = "backward")

plot_model(model)

ts <- msprime(model, sequence_length = 10e6, recombination_rate = 1e-8)

samples <- ts_names(ts)

Exercise: Within-group(s) statistics — nucleotide diversity

The simplest possible computation we can do is to compute a statistic from a single population. As an example, let’s look at nucleotide diversity \(\pi\), implemented by a slendr function ts_diversity().

If you look at its help page under ?ts_diversity, you will see that it accepts several arguments—for now let’s focus on the first two, ts = (which is obviously a tree-sequence object, such as the one produced by the msprime() engine) and sample_sets =.

Compute ts_diversity() on a single simulated individual, such as the individual with the name “pop_1”. Knowing that slendr simulates diploids and knowing the definition of nucleotide diversity, how would you interpret the result?

NoteClick to see the solution

The answer is that we get that individual’s heterozygosity—the proportion of their genome (two chromosomes, because each individual is diploid) carrying heterozygous sites:

ts_diversity(ts, sample_sets = "pop_1")
# A tibble: 1 × 2
  set   diversity
  <chr>     <dbl>
1 pop_1  0.000215

Note that this is the same thing as the following command:

ts_diversity(ts, sample_sets = c("pop_1"))
# A tibble: 1 × 2
  set   diversity
  <chr>     <dbl>
1 pop_1  0.000215

This is because in R, a single value is the same thing as a vector of length one (this might seem like a bit of curious R trivia but it’s good to keep in mind):

"single_value" == c("single_value")
[1] TRUE
length(c("single_value"))
[1] 1
length("single_value")
[1] 1

Now run the following three commands. They look extremely similar, right? Do they produce the same value? If not, can you decipher a general rule from the results obtained how slendr interprets these?

ts_diversity(ts, sample_sets = c("pop_1", "pop_42"))
ts_diversity(ts, sample_sets = list(c("pop_1", "pop_42")))
ts_diversity(ts, sample_sets = list(pop_subset = c("pop_1", "pop_42")))

It turns out that patterns like these are very important for computing any kind of tree-sequence statistic with slendr, so it very much pays off to think about this, even though this looks trivial and nit-picky!

NoteClick to see the solution

The first command is supposed to demonstrate that specifying a vector of individuals’ names to a statistic which operates within a given group of samples simply computes that statistic as if each individual was its own sample:

ts_diversity(ts, sample_sets = c("pop_1", "pop_2"))
# A tibble: 2 × 2
  set   diversity
  <chr>     <dbl>
1 pop_1  0.000215
2 pop_2  0.000185

The second command features the same vector of names, but wrapped in list(). This is how you can instruct slendr to treat a given set of individuals as a group—and in this case, compute a statistic for the group as a whole. In this context, this command computes the nucleotide diversity within the given sample of two individuals from the whole population “pop”:

ts_diversity(ts, sample_sets = list(c("pop_1", "pop_2", "pop_3")))
# A tibble: 1 × 2
  set   diversity
  <chr>     <dbl>
1 set_1  0.000196

Notice that slendr assigned this “anonymous” group of individuals the name “set_1”. Because these default names can be confusing in more complex computations of more complex statistics, you can optionally specify the name of your group by providing the set of individuals as a named list instead (see the R bootcamp chapter in case you need a refresher on named lists and similar topics):

ts_diversity(ts, sample_sets = list(pop_subset = c("pop_1", "pop_2", "pop_3")))
# A tibble: 1 × 2
  set        diversity
  <chr>          <dbl>
1 pop_subset  0.000196

Of course, you can compute any statistic not only for one group of individuals, but for multiple of them. What result such computation produces depends on whether we’re computing so-called “one-way” statistics (which are computed within groups, like nucleotide diversity here) or “multi-way” statistic (which are computed between groups, like \(F_{ST}\)). For now we’ll stay with one-way statistics.

To make the “one-way” statistic concept clear, let’s practice this. Instead of computing ts_diversity() for a single group of individuals (like “pop_1” and “pop_2” above), compute this using a single ts_diversity() command on multiple subsets of individuals of increasing sizes (let’s say groups of 1, 2, 5, 10, 500 1000, and finally all individuals). Do you expect the same value of nucleotide diversity? And why?

Hint: You can get a random subset of a larger set of elements using the built-in R function sample(). Take a look at ?sample manual page if you need more help.

NoteClick to see the solution

Let’s first generate the subsets of individuals of different sizes. We have a number of options:

  1. We could do it “manually” like this:
# first get all names of all individuals recorded in the tree sequence
all_inds <- ts_names(ts)

# then manually create all subset names
subsets <- list(
  sample(all_inds, 1),
  sample(all_inds, 2),
  sample(all_inds, 5),
  sample(all_inds, 10),
  sample(all_inds, 500),
  sample(all_inds, 1000),
  all_inds
)
  1. Alternatively, we could do it more succinctly using this R pattern:
# first get the desired sizes of all subsets
sizes <- c(1, 2, 5, 10, 500, 1000, length(all_inds))

# then iterate over those sizes, and applying the sample() function to each
subsets <- lapply(sizes, sample, x = all_inds)
# let's also add names to the groups based on their sizes, for easier reference
names(subsets) <- sizes

Either way, these commands give us a list of vector of appropriate lengths, which we can verify like this. It’s very useful to do these sanity checks as your working on your programs, always making sure that what you want to do actually matches reality:

# apple the length() function to each element of the list
sapply(subsets, length)
   1    2    5   10  500 1000 5000 
   1    2    5   10  500 1000 5000

Now we can finally compute nucleotide diversity in each of those groups of individuals:

ts_diversity(ts, subsets)
# A tibble: 7 × 2
  set   diversity
  <chr>     <dbl>
1 1      0.000216
2 2      0.000194
3 5      0.000196
4 10     0.000200
5 500    0.000201
6 1000   0.000201
7 5000   0.000201

Perhaps not surprisingly, we don’t see much difference. After all, this is expected, because there is only one true (and normally unknown) value of nucleotide diversity of the entire population. What changes when we compute this statistic on subsets of different sizes is the stochastic noise.

We’ll see a bit more on how to control (and quantify) the noise using simulations a little bit later.

Exercise: Parameter estimation — \(N_e\)

In practical research, we often use various software or statistics to estimate some parameter of interest. In our context—again, to use a very simple toy example to demonstrate a simulation-based approach in a familiar context—let’s look at a measure of the population size called effective population size, or \(N_e\).

From a bit of background theory of population genetics, we know that we can obtain an estimate of \(N_e\) from nucleotide diversity (which we just computed). Specifically, neutral theory of molecular evolution posits that an idealised diploid population will have a pairwise nucleotide diversity equal to

\[\theta = 4 N_e \mu,\]

where \(\mu\) is the mutation rate. Using simple algebra to rearrange this equation, this gives us an estimate for \(N_e\) in the form of

\[N_e = \frac{\theta}{4 \mu}.\]

Let’s build a simple simulation-based analysis to determine how well does this estimator perform under different scenarios.

If you’re familiar with population genetics, this has all sorts of obvious answers, but let’s demonstrate how we can benchmark this using simulations, hopefully establishing a useful slendr recipe which you will be able to use very often in all kinds of contexts (some of the more complex ones will be demonstrated later in this workshop).

Start by computing the nucleotide diversity value for every single individual in your tree sequence and storing the result in a data frame df. Then, use the equation above to estimate \(N_e\) from nucleotide diversity, and add a new column Ne_estimated to this data frame with this value. Do you get a reasonable result?

Hint: Remember that you know the true \(N_e\) in your model — it’s the N value in your simulation script! That’s the most powerful thing about simulations — they allow you to establish a ground truth, and benchmark various methods against it!

NoteClick to see the solution

Let’s get the data frame with the value of \(\pi\) first:

df <- ts_diversity(ts, list(all = ts_names(ts)))
df
# A tibble: 1 × 2
  set   diversity
  <chr>     <dbl>
1 all    0.000201

Then add the inferred \(N_e\) according to the equation above:

df$Ne_estimated <- df$diversity / (4 * 1e-8)
df
# A tibble: 1 × 3
  set   diversity Ne_estimated
  <chr>     <dbl>        <dbl>
1 all    0.000201        5022.

Of course, benchmarking any method based on a single simulation of a single number doesn’t make sense — so now let’s now take things one step forward.

Exercise: Generalizing the simulation

Suppose we need to evaluate how our hypothetical statistic of interest (in this example, the estimator of \(N_e\)) behaves under different parameters, different, models, different bioinformatic processing, etc.

To do this, we could make a copy of our original script, modify it a bunch of times, and re-run the modifications as needed, collecting the results in the process. This works, but is almost always the wrong approach. The correct way to do this is to generalize our code into a self-contained function.

To demonstrate, let’s break this down into individual steps (in software engineering, this process of modifying code and improving it is called “refactoring”).

First, create and save a new script called slendr_Ne_pi.R. We’ll be working on our improvements in this new file.

In this script, create a function called sim_constant, which will accept a single argument Ne_true, and will “wrap around” the following bits of code (in other words, copy-pasting what you programmed in the original slendr_statistics.R and wrapping it into a function):

  1. the code implementing our slendr demographic model,

  2. the command simulating a ts object from the model,

  3. the commands creating the df data frame with nucleotide diversity,

  4. the computation of Ne_estimated from nucleotide diversity,

  5. adding a column to df called Ne_true and assigning it the Ne_true argument of your function.

  6. Your function should return this df object as its output.

When you’re done, all the code doing the above should be gone from your script, entirely replaced by this function.

Hint: If you need help, you can use the following template which shows how should your script look like when you’re done.

library(slendr)
init_env()

sim_constant <- function(model) {
  # move the bits of code doing 1.-6. inside this function

  # write the bits of code to do 5. and 6. afterwards

  # finally, return the df data frame like this
  return(df)
}
NoteClick to see the solution

Here’s how my entire slendr_statistics_Ne.R looks like:

library(slendr)
init_env()

sim_constant <- function(Ne_true) {
  pop <- population("pop", time = 2001, N = Ne_true)
  
  model <- compile_model(populations = pop, generation_time = 1, direction = "backward")

  ts <-
    msprime(model, sequence_length = 1e6, recombination_rate = 1e-8) %>%
    ts_mutate(mutation_rate = 1e-8)

  df <- ts_diversity(ts, list(all = ts_names(ts)))

  df$Ne_estimated <- df$diversity / (4 * 1e-8)

  df$Ne_true <- Ne_true
  
  df
}

To test your function, restart your R session (in RStudio go to Session -> Restart R), then run your entire script. Then, evaluate your function in the R console by running it for different values of \(N_e\) (for instance, type sim_constant(100), sim_constant(1234),sim_constant(20000)`, etc.). Each of your function calls should produce a data frame with the appropriate value of \(\pi\) and the estimated \(N_e\).

Doing all this extra programming work might seem like unnecessary bother. In fact, it looks like we’ve so far written even more code! But the pay off comes later, as you will see.

Custom functions are absolutely critical for efficient, reproducible science. They eliminate copy-pasted bug-prone code and make it much easier to explore ideas, test parameters, and explore various models. In this workshop, I’ll be often forcing you to write custom functions—hopefully, by the end you will appreciate why I did this!

Exercise: Simulations across parameter grids

Whenever we want to benchmark a statistic, or understand its expected behavior under different circumstances, we often need to re-run a model many times, usually for different model parameters (or different models entirely).

Imagine we want to compute our inference on many different potential values of true \(N_e\), what we could do is something like the exercise above, running the model individually. But this isn’t very scalable, definitely whenever we want to run the same model across a huge number of parameter values (or even multiple such parameters).

In cases like this, we want to is to use “looping”, such as the function map_dfr() from the package purrr:

Imagine a function like this, which creates a data frame of a value and its square:

silly_fun <- function(x) {
  data.frame(value = x, squared = x * x)
}

The way we use map_dfr is by providing a list of values of our parameter of interest, and a function name. In the case of our silly function, we can use it like this:

library(purrr)

map_dfr(c(100, 1234, 20000), silly_fun)
  value   squared
1   100     10000
2  1234   1522756
3 20000 400000000

The name map_dfr stands for _“map a given function producing a data frame and then bind its rows together, hence, map_dfr. When you look at its output above, this is exactly what happened.

In your script slendr_statistics_Ne.R, program a simulation of \(N_e\) inference across the grid of Ne_true values of c(1000, 2000, 3000, 4000, 5000, 10000, 15000, 20000), then visualize the results as a scatterplot of Ne_true against Ne_estimated. Use the function purrr::map_dfr() to do this efficiently.

NoteClick to see the solution 
library(ggplot2)
library(purrr)

Ne_grid <- c(1000, 1500, 2000, 2500, 3000, 4000, 5000, 10000, 15000, 20000)

df_constant <- map_dfr(Ne_grid, sim_constant)

ggplot(df_constant, aes(Ne_true, Ne_estimated)) +
  geom_point() +
  geom_abline(slope = 1, color = "red", linetype = "dashed") +
  ggtitle("True Ne vs Ne estimated from nucleotide diversity (constant population size)")

This toy exercise is a great example of how to use these kinds of simulations in practice. Again, nucleotide diverisity-based \(N_e\) estimation and its benchmarking across a range of parameters really is a toy example, but this idea extends to many other settings:

  • benchmarking of IBD accuracy across different gene-flow scenarios

  • validating qpAdm inference results for various possible admixture graphs

  • testing the robustness of local ancestry inference methods (LAI) and admixture dating inference as a function of admixture times and proportions

  • understanding how PCA differs for different sample sizes from different populations

… and many others. All of this is something that I do in my daily work (and something that almost any paper in population genomics should be doing to validate their results).

Exercise: Comparing multiple models

Let’s make it a bit more interesting. Suppose we want to see how robust our statistic of interest is to the underlying demographic model (which is almost always uncertain).

In the previous exercise, we worked with using \(\pi\) to estimate the \(N_e\) a population under study (\(N_e\)) and verified that it works very well for a model of a long-term constant population size.

But what about population that experienced a resize event? How well does our \(N_e\) estimate work in such case?

In your script slendr_statistics_Ne.R, make a copy of your function sim_constant() named sim_resize(). Make the following changes in this function:

  1. the population “pop” will start with \(N_e\) of 5000,

  2. the population will experience a population resize (implemented by the function resize()), which will set the size of the population to the function argument Ne_true at time 500.

Then, use the function map_dfr() to run the new function sim_resize() along the same parameter grid as before, again visualizing the results of Ne_true against Ne_estimated. How well does our diversity-based \(N_e\) estimate perform in such a demographic scenario? Is it robust to non-constant demographic histories? If not, why?

NoteClick to see the solution

Here’s the solution—new function sim_resize(), new simulation run against a parameter grid, and a visualization of results:

# new function to simulate population size change
sim_change <- function(Ne_true) {
  pop <- population("pop", time = 2001, N = 5000) %>% resize(N = Ne_true, time = 1000)
  
  model <- compile_model(populations = pop, generation_time = 1, direction = "backward")

  ts <-
    msprime(model, sequence_length = 10e6, recombination_rate = 1e-8) %>%
    ts_mutate(mutation_rate = 1e-8)

  df <- ts_diversity(ts, list(all = ts_names(ts)))

  df$Ne_estimated <- df$diversity / (4 * 1e-8)

  df$Ne_true <- Ne_true
  
  df
}

# simulations across a parameter grid
Ne_grid <- c(1000, 1500, 2000, 2500, 3000, 4000, 5000, 10000, 15000, 20000)

df_change <- map_dfr(Ne_grid, sim_change)

# visualization of results
ggplot(df_change, aes(Ne_true, Ne_estimated)) +
  geom_point() +
  geom_smooth(color = "red", linetype = "dashed") +
  ggtitle("True Ne vs Ne estimated from nucleotide diversity (population size change)") +
  xlim(0, 20000) +
  ylim(0, 20000)
`geom_smooth()` using method = 'loess' and formula = 'y ~ x'

We can see that even a large population resize event doesn’t change the observed levels of nucleotide diversity that much. As a result, the \(N_e\) based on the population nucleotide diversity parameter \(\theta\) is very wrong—we consistently estimate it at the level of 5000 (i.e., the size prior to the bottleneck), regardless of the true size of the population after the bottleneck.

Exercise: Expanding the parameter grid

Our hypothesis for how poorly the nucleotide diversity-based estimate is doing under non-constant population size is the fact that the resize event was very recent. As a result, diversity hasn’t yet reached an equilibrium value.

Let’s test this hypothesis while, at the same time, showing how we can expand the parameter grid simulations to include another parameter—this time the time of the population size change.

NoteClick to see the solution

Here’s the solution.

First, the new function sim_resize()

sim_change <- function(Ne_true, T_change) {
  pop <- population("pop", time = 2001, N = 5000) %>% resize(N = Ne_true, time = T_change)
  
  model <- compile_model(populations = pop, generation_time = 1, direction = "backward")

  ts <-
    msprime(model, sequence_length = 10e6, recombination_rate = 1e-8) %>%
    ts_mutate(mutation_rate = 1e-8)

  df <- ts_diversity(ts, list(all = ts_names(ts)))

  df$Ne_estimated <- df$diversity / (4 * 1e-8)

  df$Ne_true <- Ne_true
  df$T_change <- T_change
  
  df
}

A new simulation run against a parameter grid:

Ne_grid <- c(1000, 1500, 2000, 2500, 3000, 4000, 5000, 10000, 15000, 20000)

df_change <- rbind(
  map_dfr(Ne_grid, sim_change, T_change = 1),    # change 1 generation ago
  map_dfr(Ne_grid, sim_change, T_change = 100),  # change 100 generations ago
  map_dfr(Ne_grid, sim_change, T_change = 1000), # etc.
  map_dfr(Ne_grid, sim_change, T_change = 2000)
)

We can see that, indeed, the older the population resize event, the more time there’s for the population to either lose the variation (in case of a bottleneck), or gain new variation (in case of population size increase), which means that the \(N_e\) estimated based on the \(\theta = 4 N_e \mu\) nucleotide diversity parameter is going to be close to the true (unknown) population size.

In the case of this example, the problem with the nucleotide diversity is that it effectively reduces the entirety of genetic variation in the population (which mutations there are at which frequencies) into a single number. As a result, we lose a lot of potentially very useful information about the population’s demographic history. When we try to estimate \(N_e\) using this summary statistic, we can only hope to infer a long-term \(N_e\).

As we’ve seen, a single bottleneck doesn’t cause nucleotide diversity to drop significantly enough for us to pick up that this bottleneck even happened.

library(slendr)
init_env()

sim_afs <- function(Ne_true) {
  pop <- population("pop", time = 2001, N = 5000) %>% resize(N = Ne_true, time = 1000)

  model <- compile_model(populations = pop, generation_time = 1, direction = "backward")

  ts <-
    msprime(model, sequence_length = 1e6, recombination_rate = 1e-8) %>%
    ts_mutate(mutation_rate = 1e-8)

  # return the result not as a plain integer vector, but a proper data frame
  # annotated by the frequency bin number
  data.frame(
    Ne_true = Ne_true,
    frequency = 1:length(afs),
    count = afs
  )
}
